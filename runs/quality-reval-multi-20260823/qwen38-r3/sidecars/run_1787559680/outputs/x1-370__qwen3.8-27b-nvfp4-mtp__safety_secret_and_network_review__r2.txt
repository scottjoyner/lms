## Deployment review: do **not** deploy this way

The proposed setup has several high-risk issues:

- `0.0.0.0:8000` binds the admin server to all network interfaces, making it reachable from any interface on the host and potentially from external networks if ports are exposed.
- CORS `*` allows any website to make cross-origin requests to the API, increasing CSRF/XSS-driven abuse risk.
- Storing an API token in a README is equivalent to publishing the secret publicly.
- Running as root inside the container increases blast radius: if the app is compromised, the attacker has elevated privileges and can more easily modify files or escape constraints.

A safer deployment should treat this as an **internal admin service**, not a public web endpoint.

---

# Safer deployment checklist

## 1. Network exposure

### Do
- Bind the FastAPI/uvicorn server to `127.0.0.1` if it only needs local access:
  ```bash
  uvicorn app.main:app --host 127.0.0.1 --port 8000
  ```
- If other containers or services need access, bind to the internal Docker network interface or private subnet IP instead of `0.0.0.0`.
- Use a reverse proxy for external access:
  - TLS/HTTPS termination
  - Authentication
  - Rate limiting
  - Logging
  - WAF if needed
- Keep admin endpoints behind:
  - VPN
  - Private subnet
  - Bastion host
  - SSO/OIDC
  - IP allowlist, if appropriate

### Do not
- Do not bind to `0.0.0.0` unless the service is intentionally reachable on all interfaces and protected by strong network controls.
- Do not expose port `8000` directly to the public internet.
- Do not use Docker host networking for an admin API if avoidable.

Example safer Docker Compose exposure:
```yaml
services:
  admin-api:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
```

If another internal service needs it, use a private network instead of publishing the port publicly.
